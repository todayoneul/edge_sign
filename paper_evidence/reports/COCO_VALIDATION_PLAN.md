# COCO 외부 검증 계획 (사전 등록, 2026-09-26)

**상태: 측정 전에 작성.** 예측과 판정 규칙은 결과를 본 뒤 바꾸지 않는다. 결과는 예측 번호(P1–P5)별로 "재현 / 부분 재현 / 재현 안 됨"으로 보고한다. 재현되지 않은 결과도 논문에 그대로 싣는다.

## 1. 목적

Edge-Sign(한국 도로 영상, YOLO26-n·YOLOv8s)에서 관찰한 **검출기 수준**의 결과가 표준 워크로드에서도 재현되는지 확인한다.
- 정식 MLPerf 제출(LoadGen, 시나리오, compliance)은 목표가 아니다. MLPerf가 쓰는 모델과 데이터로 같은 측정 절차를 반복하는 외부 검증이다.
- 데이터셋 사이의 절대 mAP는 비교하지 않는다. 각 워크로드 안에서 FP32 대비 유지율만 비교한다.

## 2. 워크로드

| 항목 | 설정 |
|---|---|
| 모델 | Ultralytics YOLO11l 공식 COCO 사전학습 가중치(`yolo11l.pt`). MLPerf Inference v6.0 edge YOLO 과제와 같은 모델 |
| 평가 데이터 | MLPerf COCO safe subset. COCO 2017 val 5,000장 가운데 상업 이용이 가능한 라이선스의 이미지(MLCommons `filter_coco_safe_images.py`, `create_safe_annotations.py`와 같은 라이선스 URL 규칙). 1,525장, 80클래스로 예상 |
| 보정 데이터 | MLCommons가 YOLO 보정 목록을 정하지 않았다. val2017 가운데 safe subset에 없는 이미지에서 seed 0으로 500장을 뽑는다(평가와 겹치지 않음) |
| 전처리 | 640×640 레터박스(비율 유지, 회색 114 패딩, 가운데 정렬), RGB, /255 |
| 후처리 | 신뢰도 0.001, 다중 라벨, 클래스별 NMS IoU 0.7, 이미지당 최대 300개(Ultralytics 검증 설정) |
| 정확도 지표 | pycocotools COCO mAP@0.5:0.95(주 지표), mAP@0.5 |

## 3. 변형

Edge-Sign과 같은 절차로 만든다: `quant_pre_process` → ONNX Runtime 정적 QDQ, 가중치 채널별 대칭 INT8, 활성값 비대칭 UINT8, MinMax 보정, opset 14.

| 변형 | 용도 |
|---|---|
| FP32 | 기준 |
| FP16 (FP32 입출력 유지) | 정밀도 비교 |
| INT8 전체 (INT32 bias / FP32 bias) | 붕괴 재현 여부, 실행 환경 비교(1.22 WebGPU는 FP32 bias만 실행) |
| INT8 헤드 제외 (Detect 모듈 FP32, INT32 bias / FP32 bias) | 실용 변형 |
| INT8 디코드 단계만 FP32 (INT32 bias) | 손실 분해 |
| 진단: 가중치 FP32 + 출력 연결 텐서만 양자화 | 붕괴의 충분조건(P2) |
| 진단: 가중치 FP32 + 디코드 단계 활성값에서 출력 연결만 제외 | 붕괴의 필요조건(P3) |

## 4. 사전 예측 (측정 전 기록)

- **P1 (붕괴):** INT8 전체는 신뢰도 0.001 이상의 검출을 하나도 내지 못한다(mAP 0).
  - 근거: YOLO11 출력 `[1, 84, 8400]`은 픽셀 단위 박스 좌표 4채널과 클래스 점수 80채널을 한 텐서로 연결한다.
  - 이 텐서의 보정 범위는 약 0–640이 되어, 식 (3)의 척도가 약 2.5가 된다. 그러면 점수(0–1)가 모두 영점으로 반올림된다.
- **P2 (충분조건):** 가중치를 FP32로 두고 출력 연결 텐서 하나만 양자화해도 mAP가 0이다.
- **P3 (필요조건):** 디코드 단계 활성값을 양자화하되 출력 연결 텐서만 FP32로 두면 붕괴하지 않는다(mAP > 0).
  - YOLOv8s와 같은 구조이므로, 박스 좌표 텐서의 반올림으로 인한 위치 손실은 남을 수 있다.
- **P4 (헤드 제외):** INT8 헤드 제외는 붕괴하지 않는다. 유지율 수치는 예측하지 않는다. 99% 기준과 95% 참고 등급으로 판정한다.
- **P5 (실행 환경):**
  - (a) ORT CPU와 WASM에서 INT8(전체, 헤드 제외)은 FP32보다 빠르다.
  - (b) WebGPU(ORT-Web 1.30)에서 INT8은 FP32보다 느리고, `QuantizeLinear`가 CPU에 배치된다.
  - (c) FP16은 ORT-Web 1.22 WebGPU에서 FP32보다 느리고, 1.30에서는 FP32와 비슷하거나 빠르다.

## 5. 판정

- **정확도 유지율:** R = mAP_variant / mAP_FP32 (같은 평가 코드). 99%가 기준이고 95%는 참고 등급이다.
- **MLPerf 절대 목표:** 53.4 × 0.95 / 0.99는 참고로만 적는다. MLPerf 목표는 공식 평가 코드 기준이라, 우리 코드의 FP32 값이 53.4와 다를 수 있다.
- **불확실성:** 유지율이 기준값 ±1%p 안에 들면 이미지 단위 부트스트랩으로 신뢰구간을 보고한다.

## 6. 지연 측정

- **실행 환경:** ORT CPU 1·4T, WASM 4T, WebGPU(ORT-Web 1.22·1.30). 페이지와 절차는 Edge-Sign과 같다. WASM 1T는 추론 한 번이 수 초로 예상되어 제외한다.
- **변형:** FP32, FP16, INT8 전체, INT8 헤드 제외. 1.22 WebGPU에는 FP32 bias 변형을 쓴다.
- **측정 횟수:** 기본 1,024회이다. 추론 한 번이 1초를 넘는 구성(WebGPU INT8 등)은 128회로 줄이고 표에 표시한다.
- **연산자 배치:** WebGPU 배치 로그로 P5(b)·(c)의 원인을 확인한다.
- **측정 환경 통제:** 측정 전에 프로세스별 CPU 사용량을 기록하고, 배경 동기화(iCloud Drive)를 일시정지한다.

## 7. 범위

- 검출기 한 구성요소에 대한 외부 검증이다. 인식기, 종단 정확도, 구성요소별 배치는 COCO로 검증하지 않는다.
- 측정 기기는 Edge-Sign과 같은 데스크톱 한 대이다.
